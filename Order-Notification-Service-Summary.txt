================================================================
 ORDER SERVICE & NOTIFICATION SERVICE - IMPLEMENTATION SUMMARY
 FoodSloth food delivery microservices project
================================================================

Stack: Java 17/21, Spring Boot, MongoDB, RabbitMQ (Spring AMQP),
       Maven, Lombok, JJWT (token verification only)
Scope: Order Service & Notification Service only

----------------------------------------------------------------
WHAT WAS BUILT
----------------------------------------------------------------
Two microservices were implemented against the existing project
scaffold (which already had empty order-service and
notification-service Maven modules). No other service - Cart,
User, Restaurant, Delivery, or Payment - was implemented or
modified. Communication with those services is entirely
asynchronous via RabbitMQ business events; no REST clients to
other services were created. Order Service does not read from
or write to any other service's database.

----------------------------------------------------------------
ORDER SERVICE
----------------------------------------------------------------
Owns order data and status. Single source of truth for order
lifecycle.

REST API (all endpoints require "Authorization: Bearer <jwt>")
----------------------------------------------------------------
POST   /orders
       Create an order from client-supplied items; userId is
       taken from the JWT (not the request body - see
       AUTHENTICATION below), computes subtotal/delivery
       charge/tax/grand total, saves as PENDING_PAYMENT,
       publishes PaymentRequested.

GET    /orders/{id}
       Fetch a single order. 403 if the caller is neither the
       order's owner nor an ADMIN.

GET    /orders/user/{userId}
       List a user's orders, newest first. 403 if {userId}
       isn't the caller and the caller isn't an ADMIN.

PATCH  /orders/{id}/cancel
       Cancel - only allowed while status is PENDING_PAYMENT or
       CONFIRMED (i.e. before the restaurant accepts); publishes
       OrderCancelled. Same ownership/ADMIN check as GET.

POST   /orders/{id}/reorder
       Creates a new order by replaying a previous order's items
       through the same creation flow. Same ownership/ADMIN
       check as GET.

AUTHENTICATION & AUTHORIZATION
----------------------------------------------------------------
Order Service verifies JWTs itself (does not call User Service,
does not rely on API Gateway - api-gateway currently has no auth
filter at all, it's a bare routing proxy).

- jwt.secret in order-service's application.yml is hardcoded to
  the SAME value as user-service's jwt.secret. This only works
  because the literal string is duplicated by hand right now.
  TODO: move to a shared secret store / env var so the two
  services can't silently drift out of sync.
- userId is read from the token's "sub" claim, never trusted
  from the request body or path. CreateOrderRequest has no
  userId field for this reason.
- role is read from the token's "role" claim; "ADMIN" bypasses
  ownership checks (mirrors user-service's Role enum, where
  ADMIN accounts are tied to a restaurantId).
- Missing/invalid/expired token -> 401. Valid token but wrong
  owner -> 403.

Domain model
------------
entity/Order.java
    id, userId, restaurantId, deliveryAddressId, deliveryType,
    paymentMethod, items[], subtotal, deliveryCharge, tax,
    grandTotal, status, createdAt, updatedAt

entity/OrderItem.java
    id, menuItemId, name, price, quantity, subtotal (snapshot)

entity/OrderStatus.java
    PENDING_PAYMENT, CONFIRMED, PREPARING, OUT_FOR_DELIVERY,
    DELIVERED, PAYMENT_FAILED, REJECTED, CANCELLED

entity/DeliveryType.java
    REGULAR, INSTANT

entity/PaymentMethod.java
    CARD, CASH_ON_DELIVERY, WALLET

RabbitMQ topology
------------------
Topic exchanges, one routing key per event - no generic
catch-all key.

Exchange              Routing key                  Direction  Queue (Order Service)
order.exchange         order.payment.requested       publish    -
order.exchange         order.confirmed               publish    -
order.exchange         order.cancelled                publish    -
order.exchange         order.delivered                publish    -
payment.exchange       payment.succeeded             consume    order.payment-succeeded.queue
payment.exchange       payment.failed                 consume    order.payment-failed.queue
restaurant.exchange    restaurant.order.accepted     consume    order.restaurant-accepted.queue
delivery.exchange      delivery.started               consume    order.delivery-started.queue
delivery.exchange      delivery.completed             consume    order.delivery-completed.queue

Status transitions driven by consumed events
---------------------------------------------
Event received       Guard                        New status         Publishes
PaymentSucceeded      current == PENDING_PAYMENT    CONFIRMED          OrderConfirmed
PaymentFailed         current == PENDING_PAYMENT    PAYMENT_FAILED     -
OrderAccepted         current == CONFIRMED          PREPARING          -
DeliveryStarted       current == PREPARING          OUT_FOR_DELIVERY   -
DeliveryCompleted     current == OUT_FOR_DELIVERY   DELIVERED          OrderDelivered

Note: out-of-order or duplicate events are logged and ignored
rather than applied, since each transition is guarded by the
expected prior status.

----------------------------------------------------------------
WHAT ORDER SERVICE EXPECTS FROM OTHER SERVICES
----------------------------------------------------------------
This is the contract other teams' services need to honor for
the whole pipeline to work end to end. Order Service already
declares every exchange/queue/binding listed below (topic
exchanges: order.exchange, payment.exchange, restaurant.exchange,
delivery.exchange) - other services generally just need to bind
their own queues to these exchanges and match the JSON shape.

USER SERVICE (already exists)
  - Issues JWTs on /users/signup and /users/login with the
    userId as the "sub" claim and role as a "role" claim.
  - Order Service trusts these tokens by verifying the same HMAC
    secret. As long as user-service's jwt.secret is unchanged
    (food-delivery-user-service-jwt-secret-key-change-me-2026),
    nothing further is required from User Service.
  - No RabbitMQ interaction expected from User Service.

PAYMENT SERVICE (not yet implemented)
  - Must consume PaymentRequested:
      exchange: order.exchange | routing key: order.payment.requested
      payload: { orderId, userId, amount, paymentMethod }
    Order Service has already declared a placeholder queue
    (payment.order-requested.queue) bound to this routing key so
    messages aren't dropped before Payment Service exists - once
    built, Payment Service should own/declare this queue itself
    and the placeholder can be removed from Order Service.
  - Must publish, after processing:
      PaymentSucceeded -> exchange: payment.exchange
                           routing key: payment.succeeded
                           payload: { orderId, userId, transactionId }
      PaymentFailed    -> exchange: payment.exchange
                           routing key: payment.failed
                           payload: { orderId, userId, reason }
  - Order Service only reacts if the order is still
    PENDING_PAYMENT when the event arrives; late/duplicate events
    are logged and ignored.

RESTAURANT SERVICE (not yet implemented)
  - Must consume OrderConfirmed to know a new order needs
    preparation:
      exchange: order.exchange | routing key: order.confirmed
      payload: { orderId, restaurantId, userId }
    Bind its own queue to this routing key (same pattern
    Notification Service already uses) - topic exchanges support
    multiple independent consumers on the same routing key, so
    this requires no change to Order Service.
  - Recommended (not yet required by any listener): also consume
    OrderCancelled so it can stop preparing an order that was
    cancelled after being confirmed:
      exchange: order.exchange | routing key: order.cancelled
      payload: { orderId, userId, restaurantId }
  - Must publish, once the restaurant accepts the order:
      OrderAccepted -> exchange: restaurant.exchange
                        routing key: restaurant.order.accepted
                        payload: { orderId, restaurantId }
  - Order Service only applies this if the order is currently
    CONFIRMED (i.e. payment already succeeded).
  - TODO gap: there is no "OrderRejected" event defined yet. If
    a restaurant needs to reject an order, that event/queue/
    OrderStatus.REJECTED transition still needs to be designed
    and wired into Order Service's listener layer.

DELIVERY SERVICE (not yet implemented)
  - Must publish, once a delivery person picks up the order:
      DeliveryStarted -> exchange: delivery.exchange
                          routing key: delivery.started
                          payload: { orderId, deliveryPersonId }
    Order Service only applies this if the order is currently
    PREPARING.
  - Must publish, once delivery is complete:
      DeliveryCompleted -> exchange: delivery.exchange
                            routing key: delivery.completed
                            payload: { orderId }
    Order Service only applies this if the order is currently
    OUT_FOR_DELIVERY.
  - TODO gap: nothing currently tells Delivery Service when an
    order is ready for pickup. The natural trigger is
    OrderAccepted/PREPARING, but no event carries that signal to
    Delivery Service today - Restaurant Service (or Order
    Service) would need to publish something Delivery Service
    can consume once that hand-off point is designed.
  - TODO gap: DeliveryType (REGULAR/INSTANT) and the placeholder
    delivery charges (60/120) live on the Order entity purely as
    stand-ins; Delivery Service owns the real charge calculation
    whenever that gets built.

----------------------------------------------------------------
NOTIFICATION SERVICE
----------------------------------------------------------------
Consumer-only - no REST endpoints, no database writes. Binds its
own queues to Order Service's order.exchange.

Event consumed     Queue                              Action
OrderConfirmed      notification.order-confirmed.queue Logs a notification to the user and the restaurant.
OrderCancelled      notification.order-cancelled.queue Logs a notification to the user and the restaurant.
OrderDelivered      notification.order-delivered.queue Logs a notification to the user and the restaurant.

Example log output:
    Order #{orderId} confirmed.
    Notification sent to user {userId}.
    Notification sent to restaurant {restaurantId}.

The restaurantId is only ever echoed as-is from the event
payload - Notification Service does not resolve it to an actual
admin account/contact (that would require a REST call to User
or Restaurant Service, which is out of scope here).

Email/SMS integration is intentionally out of scope; console
logging only.

NOTES & DELIBERATE PLACEHOLDERS
----------------------------------------------------------------
- Delivery charge: flat placeholder (REGULAR = 60, INSTANT = 120),
  marked with TODO; real calculation belongs to Delivery Service.
- Tax: set to 0, TODO noted; no business rule was specified.
- Payment methods: CARD / CASH_ON_DELIVERY / WALLET is a
  placeholder set pending confirmation from the Payment Service
  owner.
- payment.order-requested.queue: declared defensively in Order
  Service's own config so PaymentRequested events aren't silently
  dropped before Payment Service exists to own that queue.
- REJECTED status: defined in the enum but not yet wired to any
  listener/event - see the Restaurant Service gap above.
- jwt.secret is duplicated (by hand) between user-service and
  order-service; see AUTHENTICATION above.
- Delivery Service's trigger point (when to start a delivery) is
  not yet defined by any event - see the Delivery Service gap
  above.
